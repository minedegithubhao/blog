# RAG 正式评估集 v1 设计稿

## 1. 目标

为当前 RAG 系统建立一份可复用、可对比、可追踪的正式评估集 `v1`，用于后续所有评估运行的统一基准。

这份评估集不是临时测试样例，也不是一次性随机生成结果，而是后续不同 RAG 配置、检索策略、rerank 参数之间做横向比较时的固定试卷。

## 2. 背景与问题

当前系统已经具备：

- 评估集生成
- 评估运行
- 运行结果查看
- 运行对比

但如果评估集本身每次变化，评估结果就不具备严格可比性。

问题本质不是“能不能跑评估”，而是“跑出来的结果能不能作为正式依据”。

正式评估要满足两个条件：

1. 题集固定
2. 题目边界清晰

否则分数变化既可能来自 RAG 优化，也可能只是因为题变了。

## 3. 设计结论

### 3.1 评估集类型

本次采用：

- **固定正式评估集**
- 名称示例：`jd_help_eval_formal_v1`

而不是继续使用“一键随机生成后直接开跑”的临时评估集模式。

### 3.2 数据来源

由于当前没有真实用户历史问句数据，本次正式评估集采用：

- **FAQ 事实来源**
- **伪真实用户问法改写**

也就是：

- 答案事实必须来自现有 FAQ
- 题面表达不能照抄 FAQ 标题
- 要尽量模拟真实用户问法

这是一种“代理真实数据集”方案。

### 3.3 正式集规模

正式评估集 `v1` 总量固定为：

- `100` 条

这个规模的取舍是：

- 比 `50` 条更稳，不容易偏
- 比 `200` 条更轻，当前阶段能更快产出并进入测试

### 3.4 覆盖策略

采用：

- **全覆盖 + 高频加权**

含义是：

- 所有一级类别都必须进入正式集
- 高频场景题量更多
- 不能因为追求高频而丢掉长尾类别

### 3.5 难题比例

正式集中的难题比例固定为：

- `20%`

也就是：

- `80` 条常规题
- `20` 条难题

这里的“难题”不是故意刁钻，而是更接近真实线上问题的复杂表达。

## 4. 正式集结构

### 4.1 常规题

常规题的作用是验证主流程是否稳定，包括：

- 标准口语化改写
- 常见业务问法
- 高频 FAQ 覆盖

目标：

- 测召回稳定性
- 测分类稳定性
- 测答案关键点覆盖

### 4.2 难题

难题应覆盖以下问题类型：

- 条件省略
- 条件组合
- 口语化表达
- 易混分类
- 容易漏约束条件的问法

目标：

- 防止整体分数虚高
- 识别真正会在真实环境里出问题的场景

## 5. 单条 case 的必备字段

正式评估集中的每条 case 至少必须能稳定给出以下信息：

- `question`
- `expected_route_category`
- `expected_retrieved_faq_ids` 或 `expected_chunk_ids`
- `reference_answer`
- `key_points`
- `forbidden_points`

其中：

- `question` 表示用户实际提问
- `expected_route_category` 表示预期分类
- `expected_retrieved_*` 表示预期命中目标
- `reference_answer` 表示标准参考答案
- `key_points` 表示答对必须覆盖的点
- `forbidden_points` 表示明显错误或越界回答

## 6. 生成方式

本次不直接从生成器一步产出 `100` 条正式集，而采用“两阶段”模式。

### 阶段 1：生成候选集

先基于当前 FAQ 数据生成候选题集：

- 数量：`150` 到 `200` 条
- 规则：
  - 全覆盖
  - 高频加权
  - `20%` 难题

候选集的定位是题库，不是正式卷。

### 阶段 2：人工筛定正式集

从候选集中筛定出最终 `100` 条，固化成正式评估集 `v1`。

这一层人工筛定是正式性的关键。

## 7. 人工筛定标准

每条进入正式集的 case，必须满足以下标准。

### 7.1 事实唯一

题目背后应尽量对应明确主命中 FAQ。

不应保留这种题：

- 两个 FAQ 都算对
- 命中边界过于模糊
- 评估时容易因解释差异扯不清

### 7.2 问法像用户

题面不能太像 FAQ 标题或文档原句。

应该更接近用户实际提问风格：

- 口语
- 省略
- 简写
- 场景化

### 7.3 评判边界清晰

每条题必须清楚区分：

- 什么算答对
- 什么算答漏
- 什么算明显答错

也就是：

- `reference_answer`
- `key_points`
- `forbidden_points`

必须能支撑后续复核。

### 7.4 覆盖不重复

如果两道题只是同一事实点的轻微同义改写，不应同时保留在正式集里。

正式集追求的是：

- 覆盖面
- 代表性

而不是堆砌近义题数量。

### 7.5 难题有代表性

难题必须是真实会出问题的复杂表达，不是人工故意抬杠。

优先保留：

- 容易漏条件
- 容易混类
- 表达模糊但语义可判定

### 7.6 能稳定复跑

如果某条题的预期命中会因为轻微切分变化、排序波动而频繁漂移，这条题不适合进入正式基准集。

正式基准集第一优先级是稳定，不是极限复杂。

## 8. 版本策略

正式评估集采用版本化管理：

- 第一版：`v1`
- 后续若调整题目内容，不覆盖 `v1`
- 新题集应升级为 `v2`

原则：

- 不允许悄悄改正式集
- 正式集变更必须显式升级版本

这样做的目的是保证历史 run 的可解释性。

## 9. 使用方式

后续评估时：

- 不再频繁生成新评估集
- 优先复用正式评估集 `v1`
- 所有 RAG 版本跑同一套题

这样后续比较的对象就是：

- 检索参数变化
- rerank 参数变化
- 数据切分策略变化
- prompt 策略变化

而不是题集本身变化。

## 10. 非目标

本次设计不包含：

- 真实用户日志驱动题集建设
- 自动化 LLM 审题系统
- 多版本正式集自动回归平台
- 生产环境在线评估闭环

这些都是后续可能方向，但不是当前最紧急阶段的目标。

## 11. 推荐落地顺序

建议按以下顺序执行：

1. 生成候选集 `150` 到 `200` 条
2. 按筛定标准人工收敛到 `100` 条
3. 固化为正式评估集 `jd_help_eval_formal_v1`
4. 用这套正式集运行评估
5. 查看：
   - 分类结果
   - 检索命中结果
   - 关键指标
   - case 级失败分布

## 12. 成功标准

本次任务完成的标志不是“跑了一次评估”，而是同时满足：

1. 形成一份固定正式评估集 `v1`
2. 这份正式集可复用、可追踪、可再次运行
3. 基于该正式集跑出一轮真实评估结果
4. 能从结果里看出当前 RAG 的主要强项与薄弱点
